# DocFusion-AI 项目详细方案

## 一、建设思路

DocFusion-AI 的总体方案遵循“统一入口、分层处理、类型分流、结果回溯”的设计原则。系统不把所有文档粗暴交给单一算法处理，而是先把不同格式文件解析成统一结构，再根据文档类型和用户配置选择合适的抽取策略，最后把结果落库并返回前端展示。这样做的好处是结构清晰、便于调试，也便于后续按模块逐步优化。

从工程上看，系统划分为前端交互层、后端服务层、算法处理层、数据存储层四个部分。前端负责收集用户输入的字段表头和槽位；后端服务层负责文件上传、任务排队、进度管理与接口输出；算法处理层负责文档解析、字段抽取和标准匹配；数据存储层负责保存任务状态、解析结果、抽取结果与来源追踪信息。

## 二、系统总体流程

项目的完整业务流程如下。

1. 用户在前端输入待抽取字段，并为每个字段指定槽位，如分类、指标、数值、单位、时间、同比。
2. 用户上传待处理文档，支持 `txt`、`md`、`docx`、`xlsx`。
3. 后端创建任务，将文件写入 `backend/storage/uploads/`，并保存字段配置。
4. 系统进入解析阶段，输出标准化结构，包括段落列表、表格列表、表格视图和原始文本。
5. 系统进入抽取阶段，根据文档类型执行文本抽取或表格抽取。
6. 系统将抽取结果写入数据库，同时保留字段来源、证据和定位信息。
7. 若适合做标准化字段匹配，则继续调用匹配模块；不适合时自动跳过。
8. 前端轮询任务状态，并将最终结果、字段来源和抽取明细展示给用户。

这一流程在当前代码中由 `upload.py`、`parse.py`、`extract.py`、`match.py` 串联实现，并通过 SQLite 的 `tasks`、`document_fields`、`extracted_entities` 等表保存过程数据。

## 三、前端方案

前端采用静态页面方式实现，主页面位于 `frontend/src/pages/MainPage.js`。界面主要分为三块：字段配置区、文件上传区、结果展示区。

字段配置区允许用户动态添加表头，并选择槽位。槽位设计是系统方案中的关键，因为后端并不直接把字段名写死，而是通过槽位理解该字段在结果中的角色。例如“报考地区”通常归入分类，“招考生人数”归入数值，“统计时间”归入时间。这个设计让系统能够在不同文档中复用相同的处理逻辑。

文件上传区对文件类型、重复文件和任务状态做基础校验。用户上传后，前端把字段配置打包为 `extract_config` 一并提交后端。结果展示区则依据后端返回的结果，展示抽取出的字段值，以及对应来源段落、来源表头、表格坐标等辅助信息。

## 四、后端方案

后端基于 FastAPI 构建，统一入口在 `backend/app/main.py`。其主要职责包括接口服务、任务管理、状态推进、文档解析、字段抽取、语义匹配和结果汇总。

### 1. 任务管理

文件上传接口在 `backend/app/api/upload.py`。系统会对上传文件计算哈希值，结合处理器版本和字段配置查找缓存任务，如果命中则复用历史结果；如果未命中，则创建新任务并放入线程池处理。这样既减少重复计算，也保证了比赛演示时的响应速度。

任务状态按 `uploaded -> parsing -> parsed -> extracting -> extracted -> matching -> matched` 推进，并配有独立的 `parse_status`、`extract_status`、`match_status`，便于定位失败环节。

### 2. 文档解析

解析模块核心文件是 `backend/app/services/document_parser.py`。该模块负责把不同格式文件转成统一结构：

- `docx`：优先走 `python-docx`，异常时回退到手动 XML 解析。
- `xlsx`：优先使用 `openpyxl`，失败时回退到 `python-calamine`。
- `md`、`txt`：执行文本读取、编码容错和基础段落整理。

解析结果统一输出为：

- `doc_id`
- `doc_type`
- `paragraphs`
- `paragraph_items`
- `tables`
- `table_views`
- `raw_text`

其中 `table_views` 是后续表格抽取的重要基础，因为它保存了表头、单元格值、行列下标和 Excel 坐标。

### 3. 字段抽取

抽取主逻辑在 `backend/app/api/_extract_engine.py`，由 `extract.py` 调用。抽取模块分为两条路径。

第一条是非表格文本路径，适用于 `txt`、`md`、`docx` 中以段落为主的信息。系统会先对已解析段落做二次切分，识别更细的语义片段，再结合字段名、别名、槽位、数字模式、时间模式、同比词汇等规则生成候选结果。若有可用模型，则还会结合大语言模型进行字段理解和结果判断。

第二条是表格路径，适用于 `xlsx` 及部分结构清晰的表格视图。当前方案已优化为“表头对齐 + 按列抽取”。也就是说，系统先判断用户输入字段与原始表头之间的对应关系，再逐行读取映射列生成结果。这样做能显著降低多列名称竞争导致的字段丢失，尤其适合岗位表、统计表和业务台账。

### 4. 标准字段匹配

在抽取完成后，系统会根据文档特征判断是否进入标准字段匹配模块。匹配逻辑位于 `backend/app/api/match.py` 和 `_matcher_engine.py`。如果文档本身更像业务键值对材料，就会对抽取项进行语义匹配，映射到统一标准字段；如果文档更偏统计文本或复杂表格，则系统自动跳过这一阶段，避免无意义匹配。

### 5. 结果存储与追溯

结果存储模型定义在 `backend/app/db/models.py`。`Task` 记录整条任务生命周期；`DocumentField` 保存主结果和旧接口兼容数据；`ExtractedEntity` 保存拆解后的字段级结果，包括字段名、字段值、来源段落、来源表头、来源单元格、定位坐标和置信度等。该设计为结果追溯、前端定位显示和后续回归评测提供了基础。

## 五、算法策略方案

本项目并未把所有能力都交给大模型，而是采用“规则 + 模型 + 回退”的混合方案。

在文本抽取中，规则系统负责数字识别、日期识别、同比识别、分类词识别和结果清洗，大模型主要承担字段描述补全、复杂语义判断和局部抽取辅助。这样既控制了模型调用成本，又降低了完全依赖大模型所带来的随机性。

在表格抽取中，重点不是生成式理解，而是利用大模型或规则方法做表头映射，再按列稳定抽取。对于“用户表头”和“原始表头”表达不完全一致的情况，系统通过别名、相似度、槽位和样例值共同决策，提升列匹配成功率。

## 六、测试与验证方案

项目在 `test_data/fixtures/` 中准备了 `Excel`、`txt`、`md`、`word` 四类样例，包括统计公报、国考职位表、环境数据、药品流通分析、公共文化统计等材料。通过 `tools/run_extract_case.py` 可以批量发起上传、等待任务完成并生成抽取摘要，用于回归测试。

在验证策略上，表格和非表格应分开评估。表格类重点看列映射成功率、字段完整率和来源定位准确率；非表格重点看字段召回率、误抽率、单位命中率和同比识别准确性。当前项目已在表格抽取上取得较稳定结果，非表格文本仍需要继续优化噪声过滤和字段锚点约束。

## 七、实施与迭代方案

从实施路径上，建议继续按“三步走”推进。

第一步，稳定现有主链路。重点维护 `parse -> extract -> match` 的完整闭环，确保上传任务、缓存命中、状态恢复和结果展示稳定可用。

第二步，强化非表格抽取。需要继续优化噪声句过滤、字段锚点约束、片段级抽取和结果校验，以减少将叙述句误识别为统计结果的问题。

第三步，扩展场景与字段库。随着测试集扩大，可以逐步沉淀更多领域字段别名、槽位建议和表头映射规则，使系统从“比赛原型”逐步演进为“可复用文档处理框架”。

## 八、预期效果

按当前方案，项目可在统一界面下处理多种文件，自动完成结构解析、字段抽取与结果追踪。对于结构较清晰的表格型数据，可获得较稳定的整行抽取结果；对于统计公报类文本，可完成基础结构化输出并为人工复核提供候选信息。系统最终输出不只是“答案”，而是附带来源和证据的结构化结果，适合在教学展示、原型比赛和后续工程扩展中继续使用。
